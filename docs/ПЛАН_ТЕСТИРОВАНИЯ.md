### Критические находки (чинить в первую очередь)

1. **Unit-тесты core-svc сейчас НЕ запускаются.** `jest` падает с `module not found` (резолв `rxjs` / `@nestjs/testing`) ещё до выполнения тестов. То есть «тесты есть» ≠ «тесты проходят». Это пункт №1.
2. **У taxi-svc, gateway-api, ai-svc не установлены зависимости** — их сначала надо поставить (`npm install` / `pip install`), иначе ни запустить, ни протестировать нельзя.
3. **Покрытие неравномерное.** В core-svc спеки есть только для 6 модулей из ~17. Контроллеры (валидация DTO, guards, роли) не покрыты вообще — только сервисы.
4. **e2e-тестов нет нигде.** Есть только конфиг `test/jest-e2e.json` в core-svc, но ни одного `*.e2e-spec.ts` файла.

### Баги, найденные при тестировании (и исправленные)

- **БАГ №4 (taxi-svc).** Путаница `managerId = userId` vs `TaxiManager.id` — заявки привязывались к неверному идентификатору. Исправлено + покрыто e2e.
- **БАГ №5 (taxi-svc).** Эндпоинт `estimate-price` был недостижим из-за порядка роутов (`:id` объявлен раньше статического маршрута). Исправлено перестановкой роутов.
- **БАГ №6 (gateway-api).** Generic-прокси `/api/core|/taxi|/ai/*` слал upstream неверный путь: `extractPath` срезал только `/core`, но `globalPrefix('api')` NestJS из `req.url` НЕ снимает, поэтому `/api` оставался и upstream получал `http://core-svc:3001/api/core/...` вместо `/...` → 404. Unit-тест это маскировал (в него вручную передавали url уже без `/api`). Исправлено: `extractPath` снимает опциональный `/api` вместе с префиксом сервиса; добавлен HTTP-уровневый e2e (`proxy.routing.spec.ts`), поднимающий реальный Express.

## 1. Стратегия: три уровня тестирования

Будем тестировать на трёх уровнях, от дешёвого к дорогому. **Endpoint считается «проверенным», только когда пройдены все три.**

### Уровень 1 — Unit-тесты (Jest / pytest)
Проверяют **логику сервисов** в изоляции (Prisma/Redis замоканы). Быстро, без БД. Это то, что «говорили что нужно» для защиты.
- Что проверяем: бизнес-правила, ветки ошибок (NotFound, Forbidden, Conflict), расчёты (цена такси, рейтинг, расстояние).

### Уровень 2 — E2E / integration (Supertest для Nest, TestClient для FastAPI)
Поднимают **весь модуль HTTP-слоя** с тестовой БД, бьют реальными запросами через `request(app)`. Проверяют: guards, роли, валидацию DTO, статус-коды, формат ответа.

### Уровень 3 — Ручная проверка через Postman
«Глазами» проходим реальные сценарии на запущенном стенде (docker compose). Нужно чтобы убедиться, что сервисы реально общаются между собой (gateway → core/taxi/ai, JWT, Redis-blacklist, миграции).

## 2. Как проверять через Postman (общая методика)

### 2.1 Подготовка стенда
```bash
cd infra
cp ../.env.example .env      # заполнить JWT_SECRET, пароли БД, ADMIN_KEY и т.д.
docker compose up --build -d
docker compose ps            # все сервисы должны быть Up (healthy)
```

### 2.2 Структура Postman-коллекции
Создаём **одну коллекцию `SenimdiQAdam`** с папками по сервисам:
```
SenimdiQAdam/
├── 00 Health           (GET /health на каждом сервисе)
├── 01 Auth             (register, login, refresh, me, 2fa, ...)
├── 02 Profile
├── 03 Organizations
├── 04 News / Guides
├── 05 Reviews / Tickets / Complaints
├── 06 Admin
├── 07 Taxi (bookings, drivers, manager, chat, recurring)
└── 08 AI (chat, rag, speech, sessions)
```

### 2.3 Environment (переменные окружения Postman)
Создаём environment `local`:
| Переменная | Значение |
|-----------|----------|
| `gateway` | `http://localhost:3000/api` |
| `core` | `http://localhost:3001/api` |
| `taxi` | `http://localhost:3002` |
| `ai` | `http://localhost:8000` |
| `accessToken` | (пусто, заполняется автоматически) |
| `refreshToken` | (пусто) |
| `adminKey` | значение `ADMIN_KEY` из .env |

### 2.4 Автоматизация авторизации (главный приём)
В запросе **`POST /auth/login`** на вкладке **Tests** пишем скрипт, который сам сохраняет токен:
```javascript
const body = pm.response.json();
pm.environment.set("accessToken", body.accessToken);
pm.environment.set("refreshToken", body.refreshToken);
pm.test("login 200/201", () => pm.expect(pm.response.code).to.be.oneOf([200,201]));
```
После этого во всех защищённых запросах в **Authorization** ставим тип `Bearer Token` → значение `{{accessToken}}`. Токен подставляется сам, не нужно копировать вручную.

### 2.5 Что смотреть в каждом запросе (чек-лист)
Для каждого endpoint в Postman проверяем 4 вещи и фиксируем галочкой:
1. **Статус-код** — успех (200/201) для валидных данных.
2. **Auth** — без токена возвращает **401**, с чужой ролью — **403**.
3. **Валидация** — кривой body (нет обязательного поля, плохой email) → **400** с понятным сообщением.
4. **Формат ответа** — поля совпадают со Swagger-схемой; нет утечки `passwordHash` и прочего.

Можно вынести часть в **Tests-скрипты**, тогда Postman сам красит зелёным/красным, и можно запускать всю папку через **Collection Runner** одним кликом.

### 2.6 Где смотреть Swagger (источник истины по endpoint'ам)
- core-svc: `http://localhost:3001/api/docs`
- taxi-svc: `http://localhost:3002/docs`
- ai-svc: `http://localhost:8000/docs`
- gateway: `http://localhost:3000/api/docs`

Swagger можно **импортировать прямо в Postman** (`Import → Link → /api/docs-json`) — он сам создаст все запросы. Это самый быстрый старт.
